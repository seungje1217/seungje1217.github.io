## Kafka?

LiveSync 프로젝트에서 Redis를 정리하며 Pub/Sub 구조를 사용하면 서버끼리 메세지를 전달할 수 있다는 것을 배웠다.

> Publisher → Redis → Subscriber

근데 이벤의 양이 많아지고, 여러 서비스가 같은 이벤트를 사용하거나 이미 처리한 이벤트를 다시 읽어야한다면 Redis Pub/Sub만으로는 부족할 수 있다.

이때 자주 등장하는 것이 Kafka다.

Kafka는 대용량 데이터를 실시간으로 처리하는 분산 메시징 시스템이다..

이렇게만 들으니 너무 어려운데, 쉽게 설명하면 손님이 키오스크에서 주문하면 주문 내용에 번호가 붙고, 주문 목록에 순서대로 기록된다. 

(1번은 빅맥, 2번은 치즈버거 세트) 

주방에서는 이 주문 목록을 보고 햄버거를 만들고 음료 담당자는 같은 주문을 보고 음료를 준비한다. 각 담당자는 같은 주문표를 확인하지만 자신에게 필요한 작업만 처리한다.
햄버거를 만드는 데 시간이 조금 오래 걸려도 음료 담당자는 자신의 속도로 주문을 확인할 수 있다.
또한 주문표가 바로 사라지지 않기 때문에 작업을 놓친 직원이 있더라도 이전 주문으로 돌아가 다시 확인할 수 있다. Kafka도 이와 비슷하다.

서비스에서 발생한 주문, 결제, 회원가입 같은 이벤트에 번호를 붙여 발생한 순서대로 저장한다. 

1번 회원가입, 2번 상품 주문, 3번 결제 완료

그리고 결제, 알림, 통계 서비스가 이 기록을 각자의 속도로 읽어 필요한 작업을 처리한다. 

즉 Kafka는 메시지를 한 번 전달하고 끝나는 시스템이라기보다 주문표처럼 **발생한 일을 순서대로 기록해두고 여러 시스템이 필요한 시점에 읽을 수 있도록 만든 시스템**이다.

### 로그?

아까 Kafka는 분산 로그 시스템이라 했는데, 여기서 로그는 단순한 에러 기록이 아닌 **데이터가 발생한 순서대로 뒤에서 계속 추가되는 구조**이다. 기존 데이터를 중간에서 수정하기 보다 새로운 데이터를 마지막에 계속 추가하는거다. 이를 Append-only-Log라 하는데, 각각의 기록은 시스템에서 어떤 일이 발생하였는지를 나타낸다.

즉 Kafka에는 현재 상태만 저장하는 것이 아니라 현재 상태가 만들어지기까지 발생한 이벤트를 순서대로 저장할 수 있다.

### 왜 순서가 중요할까?

우리가 이체를 하는 상황을 생각해보자.

10000원 입금 → 3000원 출금 → 5000원 입금

순서대로 처리하면 현재 잔액은 12000원이다. 하지만 처리 순서가 달라지거나 일부 이벤트가 빠진다면 시스템마다 서로 다른 결과가 만들어질 수 있다.

분산 시스템에서는 여러 서버가 같은 데이터를 처리해야 하므로 어떤 이벤트가 먼저 발생했는지가 매우 중요하다.

결국 분산 시스템의 일관성 문제는 이벤트의 순서를 맞추는 문제라 볼 수 있는데, Kafka는 이벤트를 로그에 순서대로 기록하고 Consumer가 같은 순서로 읽을 수 있도록 해준다. 하지만 Kafka의 순서 보장은 Topic 전체가 아니라 하나의 Partition 내부에서만 보장된다.

## Kafka의 기본구조

Kafka는 Producer, Topic, Partition, Consumer로 구성된다.

### Producer

Producer는 **Kafka로 이벤트를 보내는 역할**이다.

예를 들어 주문 서비스에서 주문이 생성되면 

```JSON
{
  "orderId": 1001,
  "memberId": 10,
  "status": "ORDER_CREATED"
}
```
위와같은 이벤트를 Kafka에 전달할 수 있다.

### Topic

Topic은 **비슷한 이벤트를 모아두는 공간**이다.
주문과 관련된 이벤트는 order-events, 결제와 관련된 이벤트는 payment-events에 저장하는 방식이다.

### Partition

Partition은 **Topic을 여러 개로 나눈 단위**이다. 하나의 Topic에 이벤트가 너무 많이 들어오면 서버 한 대에서 모든 이벤트를 처리하기 어렵다.

그래서 Kafka는 Topic을 여러 Partition으로 나누어 데이터를 분산 저장한다. 여러 Partition을 사용하면 데이터를 병렬로 처리할 수 있으므로 처리량을 높일 수 있다. 하지만 앞에서 말했듯이 이벤트 순서는 각각의 Partition 내부에서만 보장된다.

따라서 예시로 같은 주문의 이벤트 순서를 유지해야한다면 oderId 같은 값을 Key로 사용하여 동일한 Partition으로 전달해야 한다.

### Offset

Offset은 **Partition 안에서 이벤트의 위치를 나타내는 번호**이다.
Consumer는 자신이 몇 번째 Offset까지 처리했는지 저장하는데, 처리 중 장애가 발생하더라도 마지막으로 처리한 Offset부터 다시 읽을 수 있다.

### Consumer

Consumer는 단순히 소비자가 아니라 **Kafka에 저장된 이벤트를 읽어서 실제 작업을 처리**하는 것이다.

각 서비스는 같은 이벤트를 사용하지만 서로 다른 작업을 수행하는데, 주문 서비스는 결제, 알림, 통계 서비스가 어떻게 동작하는지 알 필요가 없다. 이처럼 Kafka에 주문 이벤트만 발행하면 각각의 Consumer가 필요한 작업을 처리한다.

### Consumer Group

Consumer Group은 **여러 Consumer가 하나의 작업을 나누어 처리하기 위한 단위**이다. 같은 Consumer Group에 속한 Consumer들은 Partition을 나누어 처리하는데, 이를 통해 이벤트가 많아져도 Consumer를 추가하여 병렬 처리할 수 있다.

반면 서로 다른 Consumer Group은 같은 이벤트를 각각 읽는다. 결제, 알림, 통계 서비스가 서로 영향을 받지 않고 같은 주문 이벤트를 사용할 수 있는 것이다.

## Kafka는 왜 필요할까?

서비스가 적을 때는 서비스끼리 직접 API를 호출해도 큰 문제가 없다. 하지만 서비스가 많아질수록 연결 관계도 계속 복잡해진다. 

결제 서비스가 배송 서비스와 연결되고, 배송 서비스가 알림 서비스와 연결되는 식으로 시스템이 서로 강하게 의존하게 되는데 이런 구조에서는 한 서비스가 변경되거나 장애가 발생했을 때 다른 서비스에도 영향을 줄 수 있다.

이때 Kafka를 중앙 이벤트 로그로 사용하면 구조가 단순해진다.

이벤트를 발생시키는 Producer는 누가 이벤트를 사용하는지 몰라도 되고, Consumer도 이벤트가 어느 서버에서 직접 전달됐는지 알 필요 없이 자신에게 필요한 Topic만 읽으면 된다.

이처럼 Producer와 Consumer의 의존성을 줄이는 것을 **느슨한 결합(Loose Coupling)**이라고 한다.

## Kafka vs 메시지 큐

일반적인 메시지 큐는 작업을 전달하고 처리하는 데 초점이 있다. Consumer가 메시지를 처리하면 해당 메시지는 역할을 다한 것으로 보는 경우가 많다.

반면 Kafka는 Consumer가 이벤트를 읽어도 바로 삭제하지 않는다. 설정된 보존기간이나 용량 기준에 따라 이벤트를 계속 보관하는 것이다.
따라서 새로운 서비스가 추가되도 이전 이벤트부터 다시 읽을 수 있다. Consumer의 Offset을 과거로 이동하여 이벤트를 재처리하는 것도 가능한데 이를 Replay라고 한다.

## Redis Pub/Sub과 Kafka

### Redis Pub/Sub

주요목적
    - 실시간 메시지 전달

메시지 보관
    - 기본적으로 보관x

구독자 없을 때
    - 메시지 놓칠 수 있음

재처리
    - 어려움

시용 사례
    - 단순 실시간 알림

### Kafka

주요목적
    - 이벤트 저장과 스트리밍

메시지 보관
    - 설정에 따라 보관

구독자 없을 때
    - 나중에 읽기 가능

재처리
    - Offset을 이용해 가능

시용 사례
    - 대규모 이벤트 처리와 데이터 파이프라인

Redis Pub/Sub은 지금 접속 중인 서버에 빠르게 메시지를 전달하는 경우에 적합하며,
Kafka는 이벤트를 기록하고 여러 Consumer가 서로 다른 시점과 속도로 데이터를 처리해야 하는 경우에 적합하다.

## Kafka가 이벤트를 보관하는 방식

### Retention

Retention은 **시간이나 용량을 기준으로 오래된 데이터를 삭제하는 방식**이다. 사용자 행동 로그, 클릭 이벤트, 서버 매트릭처럼 일정 기간 동안만 필요한 데이터에 적합하다.

### Log Compaction

Log Compaction은 **같은 Key를 사진 이벤트 중 최신 값을 유지하는 방식**이다. 

```text
user:1 → name=짱구
user:1 → name=승제
```

이렇게 있을때 Compaction이 진행되면 user:1의 최신 상태인 name=승제를 복원할 수 있도록 레코드가 정리된다. 사용자의 프로필이나 설정처럼 key별 최신 상태를 다시 만들어야하는 경우에 사용할 수 있다. 다만 Kafka는 일반 데이터베이스처럼 원하는 데이터를 바로 SELECT할 수 있는거는 아니다.

## Kafka 사용

Kafka는 이벤트가 계속 발생하고 여러 시스템이 그 이벤트를 사용해야 할 때 유용하다.

- 주문, 결제, 배송 이벤트 처리
- 서비스 간 비동기 통신
- 사용자 행동 로그 수집
- 실시간 통계와 모니터링
- 대규모 데이터 파이프라인

반대로 단순히 작업 하나를 다른 서버에 전달하거나, 규모가 작은 서비스에서 짧은 메시지만 처리하는 경우에는 Kafka가 지나치게 복잡할 수 있다. Kafka를 운영하려면 Partition 수, 복제, Offset, Consumer Lag, 장애 복구 등을 함께 관리해야 하기 때문이다.

## 정리

Kafka는 Producer가 보낸 이벤트를 Topic에 저장하고 Consumer가 필요한 이벤트를 읽는 분산 이벤트 스트리밍 시스템이다.

하지만 가장 중요한 것은 단순히 메시지를 전달한다는 점이 아니다. Kafka는 시스템에서 발생한 이벤트를 순서가 있는 로그로 기록하고 보관한다.

```text
이벤트 발생 → Kafka 로그에 순서대로 저장 → 여러 Consumer가 각자의 속도로 처리 → 필요한 경우 과거 이벤트부터 다시 처리
```

그리고 결제 서비스, 알림 서비스, 통계 서비스가 이 기록을 각자의 속도로 읽어서 필요한 작업을 처리한다.

즉 Kafka는 메시지를 한 번 전달하고 끝나는 시스템이라기보다, 주문표처럼 **발생한 일을 순서대로 기록해두고 여러 시스템이 필요한 시점에 읽을 수 있도록 만든 시스템**이다.
