최근 정보처리기사 실기 시험에서 1번부터 블랙박스 테스트와 관련된 문제가 나왔는데 틀려버렸다..

그래서 이번에는 다시 공부하는 겸 블랙박스 테스트가 무엇인지 어떤 방식으로 테스트 케이스를 만드는지 정리해보려고 한다.

소프트웨어를 테스트한다고 하면 보통 코드를 한 줄씩 확인하는 모습을 먼저 떠올리게 된다.

하지만 사용자는 프로그램의 내부 코드를 알지 못한다.

로그인 버튼을 눌렀을 때 로그인이 되는지, 잘못된 비밀번호를 입력했을 때 오류 메시지가 나타나는지만 확인할 뿐이다.

이처럼 프로그램의 내부 구조를 보지 않고 입력과 출력만으로 기능을 검증하는 방법이 **블랙박스 테스트(Black Box Testing)**다.

## 블랙박스 테스트?

블랙박스 테스트는 소프트웨어의 내부 코드나 동작 구조를 보지 않고, 요구사항을 기준으로 기능이 올바르게 동작하는지 확인하는 테스트 방법이다.

```text
입력값 → 내부를 알 수 없는 프로그램 → 실행 결과
```

테스터는 프로그램 안에서 어떤 알고리즘이 사용되는지, 조건문이 어떻게 작성됐는지 알 필요가 없다.

대신 2가지를 비교한다.

```text
사용자가 값을 입력
        ↓
실제 실행 결과 확인
        ↓
요구사항의 예상 결과와 비교
```

예를 들어보자.

```text
올바른 이메일과 비밀번호를 입력하면 로그인에 성공한다.  
잘못된 정보를 입력하면 오류 메시지를 보여준다.
```

로그인 기능의 요구사항이 다음과 같을때 테스터는 실제로 이메일과 비밀번호를 입력한 뒤 로그인 성공 여부와 오류 메시지를 확인할거다.

로그인 기능 내부에서 데이터베이스를 어떻게 조회하는지, 비밀번호를 어떻게 비교하는지는 확인하지 않는다.

블랙박스 테스트는 검은 상자 안에 물건을 넣어보고 무엇이 나오는지만 확인하는 것과 비슷해서 블랙박스 테스트라고 부른다.


## 블랙박스 테스트의 기준

블랙박스 테스트의 기준은 코드가 아니라 **요구사항과 명세**다.


- 비밀번호는 8자 이상 20자 이하
- 이메일은 올바른 형식
- 필수 항목은 비워둘 수 없음
- 이미 가입된 이메일은 사용할 수 없음

회원가입 기능에 위와 같은 조건이 있을때 테스터는 이 조건을 보고 테스트 케이스를 만든다.

```text
비밀번호 7자 입력  → 가입 실패
비밀번호 20자 입력 → 가입 성공
비밀번호 21자 입력 → 가입 실패
```

내부 코드가 아무리 깔끔하게 작성됐더라도 8자의 비밀번호로 가입할 수 없다면 요구사항을 만족하지 못한 것이다.

즉 블랙박스 테스트에서 중요한 것은 **코드가 어떻게 작성됐는가**가 아니라 **사용자가 원하는 기능이 제대로 동작하는가**다.


## 블랙박스 테스트 기법

모든 입력값을 하나씩 테스트하는 것은 사실상 불가능하다..비밀번호 입력칸만 해도 만들 수 있는 문자열의 조합이 너무 많기 때문이다.

그래서 블랙박스 테스트에서는 적은 수의 테스트 케이스로 많은 오류를 찾기 위한 여러 기법을 사용한다.

### 동등 분할 검사

(이번에 틀린 문제의 정답이다,,)
동치 분할 검사(Equivalence Partitioning)는 비슷하게 처리될 것으로 예상되는 입력값을 하나의 그룹으로 나누는 방법이다.

나이 입력 범위가 20세 이상 60세 이하일때 입력값은 다음 세 그룹으로 나눌 수 있다.

```text
20 미만 (유효x) → 실패 
20~60 (유효) → 성공
60 초과 (유효x) → 실패 
```

각 그룹의 값이 같은 방식으로 처리된다고 보고 **대표값**만 선택한다.

```text
10 입력 → 실패 그룹 확인
30 입력 → 성공 그룹 확인
70 입력 → 실패 그룹 확인
```

1부터 100까지 모든 숫자를 테스트하지 않아도 세 그룹의 동작을 확인할 수 있다.

즉 동치 분할 검사는 **입력값을 의미 있는 그룹으로 묶어 테스트 수를 줄이는 방법**이다.

### 경계값 분석

경계값 분석(Boundary Value Analysis)은 입력 범위의 경계와 그 주변 값을 집중적으로 테스트하는 방법이다.

프로그램의 오류는 범위의 중간보다 시작과 끝에서 자주 발생하는데 개발자가 `20세 이상`을 구현하면서 `age > 20`이라고 작성하면 21세부터는 정상 동작하지만 20세인 사용자는 실패한다.

나이 범위가 20세 이상 60세 이하라면 다음 값을 확인할 수 있다.

```text
19 → 최소값 바로 아래
20 → 최소값
21 → 최소값 바로 위

59 → 최대값 바로 아래
60 → 최대값
61 → 최대값 바로 위
```

동치 분할 검사가 입력을 그룹으로 나눈다면, 경계값 분석은 **그 그룹이 나뉘는 경계 주변을 자세히 확인하는 방법**이다. 두 기법은 함께 사용하는 경우가 많다.

### 결정 테이블

결정 테이블(Decision Table Testing)은 여러 조건의 조합에 따라 결과가 달라질 때 사용하는 방법이다.

로그인 기능을 예로들면 로그인 결과는 이메일과 비밀번호가 각각 올바른지에 따라 달라진다.

| 이메일 | 비밀번호 | 예상 결과 |
|---|---|---|
| 일치 | 일치 | 로그인 성공 |
| 일치 | 불일치 | 로그인 실패 |
| 불일치 | 일치 | 로그인 실패 |
| 불일치 | 불일치 | 로그인 실패 |

조건을 표로 정리하면 빠뜨린 조합이 있는지 쉽게 확인할 수 있다.

쿠폰 적용처럼 회원 등급, 주문 금액, 쿠폰 유효기간 등 여러 조건이 동시에 결과에 영향을 주는 기능에서 특히 유용하다.

### 원인-효과 그래프 검사

원인-효과 그래프 검사(Cause-Effect Graphing Testing)는 입력 조건을 원인으로 그에 따라 발생하는 결과를 효과로 보고 관계를 그래프로 표현하는 방법이다.

```text
원인
- 이메일이 일치함
- 비밀번호가 일치함

효과
- 로그인 성공
- 오류 메시지 출력
```

예를 들어 로그인 기능에서 위와 같은 원인과 효과가 있을때 두 입력 조건이 모두 참일 때만 로그인에 성공한다.


이메일 일치 AND 비밀번호 일치 → 로그인 성공


조건 사이의 관계가 복잡할 때 원인과 결과를 시각적으로 정리하면 누락된 조합을 찾기 쉬워진다. 보통 원인-효과 그래프를 만든 뒤 이를 결정 테이블로 변환하여 실제 테스트 케이스를 작성한다.

### 상태 전이 테스트

상태 전이 테스트(State Transition Testing)는 이전 상태나 동작에 따라 결과가 달라지는 기능을 테스트하는 방법이다.

```text
로그인 가능 상태
    ↓ 비밀번호 1회 실패
실패 횟수 1회
    ↓ 계속 실패
실패 횟수 5회
    ↓
계정 잠금 상태
```

위처럼 비밀번호 입력 기회가 5번인 로그인 기능이 있을때 같은 비밀번호를 입력하더라도 현재 상태가 다르면 결과가 달라진다.

실패 횟수가 4회인 상태에서 잘못된 비밀번호 입력 → 계정 잠금
계정이 잠긴 상태에서 올바른 비밀번호 입력 → 로그인 실패
잠금이 해제된 뒤 올바른 비밀번호 입력 → 로그인 성공

이처럼 상태 전이 테스트는 로그인 잠금, 주문 상태, 문서 승인 과정처럼 **상태와 순서가 중요한 기능**에 적합하다.

### 유스케이스 테스트

유스케이스 테스트(Use Case Testing)는 사용자가 실제로 서비스를 이용하는 전체 흐름을 기준으로 테스트하는 방법이다.

```text
로그인 → 상품 검색 → 장바구니 추가 → 배송지 입력 → 결제 → 주문 완료
```

위와같은 쇼핑몰의 상품 구매 과정에서 각 기능을 따로 테스트했을 때는 문제가 없어도 기능이 연결되는 과정에서 오류가 발생할 수 있다.

유스케이스 테스트는 **사용자의 입장**에서 처음부터 끝까지 기능을 실행하기 때문에 이런 문제를 찾는 데 도움이 된다.

### 오류 예측

오류 예측(Error Guessing)은 테스터의 경험을 바탕으로 문제가 생길 만한 값을 예상해 테스트하는 방법이다.

입력값을 비워두기, 공백만 입력하기, 매우 긴 문자열 입력하기, 특수문자 입력하기, 네트워크가 끊긴 상태에서 요청하기 등 

정해진 공식보다는 경험과 직관에 의존하기 때문에 다른 테스트 기법을 보완하는 용도로 사용한다.

### 비교 검사

비교 검사(Comparison Testing)는 같은 기능을 수행하는 여러 프로그램이나 버전의 실행 결과를 비교하는 방법이다.

기존 결제 시스템을 새로운 시스템으로 교체할때

```text
같은 주문 정보를 기존 시스템에 입력
같은 주문 정보를 새로운 시스템에 입력
                ↓
두 시스템의 결제 금액과 결과를 비교
```

두 결과가 다르다면 어느 한쪽에 문제가 있는거다. 기존 시스템과 새 시스템, 서로 다른 알고리즘이나 여러 구현체가 같은 결과를 내야 하는 상황에서 사용할 수 있다.


## 화이트박스 테스트와 차이

블랙박스 테스트와 자주 비교되는 방식이 화이트박스 테스트(White Box Testing)다.

화이트박스 테스트는 내부 코드와 로직을 확인하며 테스트한다.

```text
블랙박스 테스트 → 사용자의 관점에서 기능 확인
    올바른 정보로 로그인되는가?
    잘못된 정보에 오류 메시지가 나오는가?

화이트박스 테스트 → 개발자의 관점에서 내부 로직 확인
    로그인 코드의 모든 조건문이 실행되는가?
    예외 처리 코드까지 테스트됐는가?
```

두 방식 중 하나가 더 좋은 것은 아니다. 블랙박스 테스트만 하면 내부의 실행되지 않은 코드나 숨겨진 로직 문제를 놓칠 수 있고 화이트박스 테스트만 하면 코드에는 구현되지 않았지만 요구사항에는 존재하는 기능을 놓칠 수 있다.

그래서 실제 테스트에서는 두 방식을 함께 사용한다.


## 정리

### 블랙박스 장단점

#### 장점

- 내부 코드를 몰라도 테스트 가능
- 사용자의 관점에서 기능 검증 가능
- 요구사항에서 빠졌거나 잘못 구현된 기능을 찾기 쉬움
- 개발자와 독립된 관점으로 테스트 가능
- 웹, 앱, API 등 다양한 환경에 적용 가능

#### 단점

- 내부 코드의 어떤 부분에서 오류가 발생했는지 알기 어려움
- 모든 입력과 실행 경로를 테스트 불가
- 요구사항이 불명확하면 올바른 결과 판단 어려움
- 이미 내부적으로 테스트된 기능을 중복해서 확인할 수도 있음
- 테스트 케이스를 잘못 선정하면 중요한 오류를 놓칠 수 있음


결국 블랙박스 테스트의 핵심은 프로그램 내부가 어떻게 동작하는지를 확인하는 것이 아니다.

**사용자가 어떤 값을 입력했을 때 약속한 결과가 제대로 나오는지를 확인하는 것**이다.
